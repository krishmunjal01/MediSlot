Academic Demonstration: POJO vs. Spring-Managed Bean

This section demonstrates the fundamental difference between standard unmanaged Java objects (POJOs) and Spring-managed IoC container singletons (Beans), as required by the faculty case study.

Standard Java

Plain Old Java Object (POJO)

Class: com.medislot.model.AppointmentSummaryPOJO

Creation: Instantiated explicitly using new keyword in memory.

Lifecycle: Standard JVM Heap allocation, garbage-collected when out of scope.

Live Instantiated POJO Instance:

Reference: Ref
Patient: Eleanor
Doctor: Dr. Arjun
Status: CONFIRMED
Summary Output: Summary

Code Sample:

// Instantiated explicitly by application code
AppointmentSummaryPOJO pojo = new AppointmentSummaryPOJO(
    "APT-20261115-DEMO",
    "Eleanor Vance",
    "Arjun Mehta",
    "Cardiology",
    LocalDate.now(),
    LocalTime.of(10, 30),
    "CONFIRMED",
    750.00
);
// Domain method encapsulated within POJO
String summary = pojo.getFormattedSummary();
Inversion of Control

Spring-Managed Bean

Class: com.medislot.service.impl.AppointmentServiceImpl

Creation: Created & managed by Spring IoC Container via @Service.

Lifecycle: Singleton managed throughout application context, wrapped with CGLIB proxy for @Transactional.

Live Spring Bean Properties:

Bean Type: Service Component Singleton
Injection Mode: Constructor Dependency Injection
Transactional Proxy: Active (Isolation = REPEATABLE_READ)
Pessimistic Locking: Integrated via SELECT FOR UPDATE

Code Sample:

@Service
public class AppointmentServiceImpl implements AppointmentService {

    // Constructor-based Dependency Injection
    public AppointmentServiceImpl(
        AppointmentRepository aptRepo,
        AppointmentSlotRepository slotRepo,
        AuditService auditService) { ... }

    @Override
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public Appointment bookAppointment(...) { ... }
}

Core Object-Oriented Programming Pillars in MediSlot

OOP Principle Implementation in MediSlot Live Architecture Evidence
Encapsulation Private fields with controlled getters/setters and domain state-transition validation. Patient.java, Doctor.java, AppointmentStatus.java (e.g. canBeCancelled())
Inheritance Abstract base User class extended by 4 specialized system actors. User → Admin, Doctor, Receptionist, Patient
Polymorphism Subclasses override abstract polymorphic methods providing distinct behavior. getDashboardUrl(), getRoleDescription() overridden across all 4 user classes
Abstraction High-level interfaces decouple business services from database persistence details. AppointmentService, PatientRepository, DoctorRepository
Method Overloading Methods sharing a name but differentiated by parameter types for clean API design. findById(Long) vs findByPatientCode(String) in TraditionalPatientJdbcRepository
Custom Exceptions Meaningful exception hierarchy with centralized HTTP translation. SlotUnavailableException, DuplicateBookingException with @ControllerAdvice
